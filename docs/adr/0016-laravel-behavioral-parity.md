# Follow Laravel behavior unless Node cannot provide equal safety

Holo adopts Laravel's behavior, defaults, and failure semantics for equivalent capabilities, so Laravel developers can predict how an application behaves. A Holo capability departs from Laravel only where JavaScript or Node cannot provide the safety PHP provides, and each departure is recorded with that reason. We chose behavioral parity over case-by-case redesign because familiar semantics reduce surprise and give one tie-breaker for future decisions; it rejects opinionated hardening that Laravel itself does not apply.

Recorded departures:

- Request input is bounded at 1,000 non-file input variables and, separately, 1,000 uploaded-file entries per form, and array indexes must fall within the submitted entries, because Node lacks PHP's `max_input_vars` and JavaScript arrays are sparse rather than hash maps. Names are limited to PHP's default `max_input_nesting_level` of 64 levels after the root; PHP silently drops deeper variables, while Holo rejects the request, just as it rejects excess variables instead of truncating them. A name may not mix numbered indexes with appended or repeated values; PHP accepts it order-dependently, overwriting values, so Holo rejects it to keep one name to one shape.
- Path segments that reach object prototypes are rejected, because PHP arrays have no prototype chain.
- Request, subscription, and capability state must be isolated per request or subscription, because a Node process outlives requests while PHP shares nothing between them.
- A malformed typed environment value fails instead of returning the raw string, because a typed fallback cannot represent Laravel's string result.
- `APP_ENV` must be `development`, `production`, or `test`, and any other value fails, because Holo's environment is a typed value that selects a fixed env-file order and production safeguards; an unknown name would otherwise fall back silently.
- `APP_ENV` in `.env` also selects the environment's env files, loaded on top of `.env`, because Node has no process-wide `putenv` step before the framework boots, so `.env` is the only file an operator can rely on to name the environment for every Holo entry point.
- Holo encrypts only the cookies it owns (session, remember, and `XSRF-TOKEN`), because it cannot intercept cookies written through each framework's native cookie interfaces as Laravel's `EncryptCookies` does.
- Model primary keys and `created_at`/`updated_at` columns are guarded unless named in `fillable`, even with `fillable: ['*']` or a `guarded` list, because Holo applies mass-assignment rules to query updates and upserts that receive request payloads, where Laravel applies none.
- Password and sensitive fields are stripped from validation failures at every depth, including arrays, because Holo echoes submitted values in 422 response bodies and exception payloads, while Laravel flashes input only into the server-side session.
- The Nuxt form-failure cookie carries errors but no submitted values, because it is a client-readable cookie rather than Laravel's server-side session.
- Social sign-in links an existing local user only when that user's email is verified, because Laravel core defines no social account-linking behavior.
- Local disk file names ending in `$` are reserved, because Holo keeps low-level metadata in `<name>$` sidecar files on local disks, while Flysystem has no metadata sidecars.
- With `trustedProxies: '*'`, forwarded headers are trusted when the framework does not expose the connection address, and with a list of proxies they are ignored, because Next.js gives Holo no equivalent of PHP's always-present `REMOTE_ADDR`.
- A malformed trusted `X-Forwarded-Port` or `X-Forwarded-Prefix` is answered with `400 Bad Request`, as a malformed forwarded host is in Laravel, because a URL object cannot hold the non-numeric port PHP casts to an integer, and Holo places the prefix in the public request path, where a prefix such as `//host` would read as another origin.
- Holo applies set mutators when an attribute is written, not when it is assigned, so `make()`, `set()`, and `fill()` store the raw assigned value and a mutated value is visible only after `save()`, because Holo runs one write path for `create()`, `save()`, `update()`, and query updates, and a mutator then runs once per write. Laravel runs set mutators on assignment, so reads before save differ; assignment-time mutation changes what getters return and is deferred to a later release.
- The memory rate-limit store keeps at most 10,000 keys per process and never evicts a live counter: when it is full it drops expired keys, then limits new keys until one expires, because Node processes grow without bound under a flood of distinct keys, which PHP's per-request arrays never reach, and evicting a live counter would let an attacker reset a victim's attempts. This is a hardening beyond Laravel, whose array driver is unbounded, and the file store deletes expired keys on a background sweep for the same reason.
- The config cache file is written with mode `0600`, because it holds evaluated secrets such as `APP_KEY`, and file permissions are the only access control Holo has over it. Laravel leaves its cache at default permissions; this is a hardening, not a behavioral departure.
- The `_token` field and `X-CSRF-TOKEN` header accept the encrypted `XSRF-TOKEN` cookie value as well as the plain session token, because browser submitters, including Next.js Server Actions, can neither read the plain token nor always set request headers. The check is the same as Laravel's `X-XSRF-TOKEN` path: decrypt with the cookie's name and key, then compare with the session token in constant time.
- CORS configuration rejects wildcard origins combined with credentials, where Laravel's CORS middleware reflects the request's origin, because reflecting any origin with credentials lets every website read cookie-authenticated responses.
- Each Broadcast connection holds at most 100 channels and 100 realtime query subscriptions, sends at most 200 messages in each one-second window, and may have at most 4 MiB of output waiting for it; a connection that exceeds the message rate or the output bound is closed with code `1008`. Laravel does not bound a connection this way itself, but its ecosystem does: Laravel Reverb sets `max_message_size` and per-app connection and event-rate limits. Holo's worker keeps every connection in one Node process, so a slow reader or a flood of messages would otherwise hold unbounded memory and block the event loop for other connections. Holo enforces these as fixed defaults in 0.4.0 and does not expose them as configuration.
- `queue:listen` forwards `SIGINT` and `SIGTERM` to its worker, waits for the worker to close before a restart or exit, and stops with the error when the worker reports a process error while it is being stopped instead of starting a replacement. Laravel's `queue:listen` forwards no signals and respawns its worker after every exit regardless of exit code. Node does not kill a child process when its parent exits, so an unforwarded signal leaves a worker running with nothing supervising it, and a replacement started after a process error may run beside a worker that never closed; both would let two workers process the same queue.
