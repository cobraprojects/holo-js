# Follow Laravel behavior unless Node cannot provide equal safety

Holo adopts Laravel's behavior, defaults, and failure semantics for equivalent capabilities, so Laravel developers can predict how an application behaves. A Holo capability departs from Laravel only where JavaScript or Node cannot provide the safety PHP provides, and each departure is recorded with that reason. We chose behavioral parity over case-by-case redesign because familiar semantics reduce surprise and give one tie-breaker for future decisions; it rejects opinionated hardening that Laravel itself does not apply.

Recorded departures:

- Request input is bounded at 1,000 non-file input variables and, separately, 1,000 uploaded-file entries per form, and array indexes must fall within the submitted entries, because Node lacks PHP's `max_input_vars` and JavaScript arrays are sparse rather than hash maps. Names are limited to PHP's default `max_input_nesting_level` of 64 levels after the root; PHP silently drops deeper variables, while Holo rejects the request, just as it rejects excess variables instead of truncating them. A name may not mix numbered indexes with appended or repeated values; PHP accepts it order-dependently, overwriting values, so Holo rejects it to keep one name to one shape.
- Path segments and model attribute names that reach object prototypes (`__proto__`, `constructor`, `prototype`) are rejected, and attribute reads return only own properties, because PHP arrays have no prototype chain.
- Request, subscription, and capability state must be isolated per request or subscription, because a Node process outlives requests while PHP shares nothing between them.
- A malformed typed environment value fails instead of returning the raw string, because a typed fallback cannot represent Laravel's string result.
- `APP_ENV` must be `development`, `production`, or `test`, and any other value fails, because Holo's environment is a typed value that selects a fixed env-file order and production safeguards; an unknown name would otherwise fall back silently.
- `APP_ENV` in `.env` also selects the environment's env files, loaded on top of `.env`, because Node has no process-wide `putenv` step before the framework boots, so `.env` is the only file an operator can rely on to name the environment for every Holo entry point.
- Holo encrypts only the cookies it owns (session, remember, and `XSRF-TOKEN`), because it cannot intercept cookies written through each framework's native cookie interfaces as Laravel's `EncryptCookies` does.
- Model primary keys and `created_at`/`updated_at` columns are guarded unless named in `fillable`, even with `fillable: ['*']` or a `guarded` list, because Holo applies mass-assignment rules to query updates and upserts that receive request payloads, where Laravel applies none.
- An instance `save()` or `delete()` applies the model's global scopes to its UPDATE or DELETE, so a row a scope hides is not written, while soft-deleted rows are updated as Laravel's `performUpdate()` does. Laravel's `performUpdate()` ignores global scopes, but a tenant scope on an instance write is the only guard against a stale entity writing into another tenant's rows, which Holo's scope isolation tests rely on.
- Password and sensitive fields are stripped from validation failures at every depth, including arrays, because Holo echoes submitted values in 422 response bodies and exception payloads, while Laravel flashes input only into the server-side session.
- The Nuxt form-failure cookie carries errors but no submitted values, because it is a client-readable cookie rather than Laravel's server-side session.
- Social sign-in links an existing local user only when that user's email is verified, because Laravel core defines no social account-linking behavior.
- Local disk file names ending in `$` are reserved, because Holo keeps low-level metadata in `<name>$` sidecar files on local disks, while Flysystem has no metadata sidecars.
- With `trustedProxies: '*'`, forwarded headers are trusted when the framework does not expose the connection address, and with a list of proxies they are ignored, because Next.js gives Holo no equivalent of PHP's always-present `REMOTE_ADDR`.
- When the client address is unknown, `ip()` and IP-keyed rate limits throw a configuration error instead of counting the request under a shared or per-request key. A shared key lets one client lock out every visitor, and a per-request key disables throttling. This departs from Laravel, where a request behind an untrusted proxy is counted under the proxy's address, because Holo fails closed and names `TRUSTED_PROXIES` in the error.
- A malformed trusted `X-Forwarded-Port` or `X-Forwarded-Prefix` is answered with `400 Bad Request`, as a malformed forwarded host is in Laravel, because a URL object cannot hold the non-numeric port PHP casts to an integer, and Holo places the prefix in the public request path, where a prefix such as `//host` would read as another origin.

- Remember recallers carry an authenticated expiry and the server rejects them after the configured lifetime, even if a client replays the cookie. This user-approved hardening bounds stolen-cookie replay independently of browser `Max-Age`, unlike Laravel.
- A session restored from a remember cookie is not recent authentication, so it cannot begin or confirm multi-factor enrollment until the user signs in with a password. Laravel gates such operations with a password confirmation; Holo has no password-confirmation step yet, so an explicit password login is the only way to refresh authentication. This is a hardening departure.
- Remember restoration rotates the session ID when it persists a session, as Laravel's `SessionGuard::updateSession()` does on every login. The planted-session attack this closes is a consequence of shared `SESSION_DOMAIN` across subdomains, so rotation is parity, not a departure.
- Confirming multi-factor enrollment cycles the user's remember token, so every remember cookie issued before enrollment stops restoring. Laravel's Fortify does not rotate on two-factor enable, which leaves a stolen remember cookie able to restore a session that skips the new TOTP challenge. The enrolling browser keeps its authenticated session, and it receives a fresh remember cookie only when that login was itself remembered. This is a hardening departure, not a Laravel behaviour.
- Holo applies set mutators when an attribute is written, not when it is assigned, so `make()`, `set()`, and `fill()` store the raw assigned value and a mutated value is visible only after `save()`, because Holo runs one write path for `create()`, `save()`, `update()`, and query updates, and a mutator then runs once per write. Laravel runs set mutators on assignment, so reads before save differ; assignment-time mutation changes what getters return and is deferred to a later release.
- Set mutators run in place on the model's own attributes during `save()`, and a save that succeeded stays applied when the caller then rolls back the transaction around it, as Laravel's Eloquent does. The model still `exists()`, keeps the mutated values, and is clean, so a retry `save()` with no changes writes nothing; a rolled-back insert leaves no row while the model still `exists()`, and a rolled-back update leaves the row with its pre-transaction values while the model keeps the new ones. To write the record again, create a new model with `make()` and `save()`, or reload a loaded model with `refresh()`, which throws for a model that was never saved. When a save fails, `writeUnit()` restores the model unless the save ran inside a transaction the caller started and its SQL had already completed; in that case the write stays in the transaction and the model keeps its written state. A save that runs at root scope gets its own transaction from Holo, so it restores on failure. A failed save that failed before its SQL completed also restores. When the COMMIT that ends a transaction fails, the model's persisted bookkeeping (`exists`, original values, and changes) returns to what it was before the transaction's first save, and values the write generated, such as an `id`, are cleared. Attributes the caller assigned, including later edits, keep their values and stay dirty so a retry writes them (`EntityCommitRestore.restore()` in `packages/db/src/model/Entity.ts`). This applies whether Holo or the caller started that transaction. That restore goes further than Laravel. Restoring after a caller's rollback would need copy-and-commit, which changes what `saving` and `updating` listeners see, so it is not done. The in-place behavior was approved as a deviation in the combined review round 2 (#317 item 2; #327, #338).
- Raw SQL predicates in `update()` and `delete()` are gated by `allowUnsafeRawSql` as reads already are, because a raw condition built from user input there can change every row; Laravel's `whereRaw` has no policy gate. Framework-owned token redemption uses a closed database-clock predicate that bypasses the gate and takes no SQL from the caller.
- The memory cache keeps at most 10,000 entries unless `maxEntries` is set, and evicts the oldest first, because a process-lifetime store grows without bound; Laravel's array driver lives only for one request.
- The memory rate-limit store keeps at most 10,000 keys per process and never evicts a live counter: when it is full it drops expired keys, then limits new keys until one expires, because Node processes grow without bound under a flood of distinct keys, which PHP's per-request arrays never reach, and evicting a live counter would let an attacker reset a victim's attempts. This is a hardening beyond Laravel, whose array driver is unbounded, and the file store deletes expired keys on a background sweep for the same reason.
- The config cache file is written with mode `0600`, because it holds evaluated secrets such as `APP_KEY`, and file permissions are the only access control Holo has over it. Laravel leaves its cache at default permissions; this is a hardening, not a behavioral departure.
- The `_token` field and `X-CSRF-TOKEN` header accept the encrypted `XSRF-TOKEN` cookie value as well as the plain session token, because browser submitters, including Next.js Server Actions, can neither read the plain token nor always set request headers. The check is the same as Laravel's `X-XSRF-TOKEN` path: decrypt with the cookie's name and key, then compare with the session token in constant time.
- CORS configuration rejects wildcard origins combined with credentials, where Laravel's CORS middleware reflects the request's origin, because reflecting any origin with credentials lets every website read cookie-authenticated responses.
- Broadcast workers ping Node WebSocket connections every 30 seconds and terminate those that don't answer, and presence members are tied to a per-worker Redis lease that expires after 30 seconds, because a half-open socket or a crashed process can't run its own cleanup, so without these bounds its connection or presence membership would persist until a restart.
- Each Broadcast connection holds at most 100 channels and 100 realtime query subscriptions, sends at most 200 messages in each one-second window, and may have at most 4 MiB of output waiting for it; a connection that exceeds the message rate or the output bound is closed with code `1008`. Laravel does not bound a connection this way itself, but its ecosystem does: Laravel Reverb sets `max_message_size` and per-app connection and event-rate limits. Holo's worker keeps every connection in one Node process, so a slow reader or a flood of messages would otherwise hold unbounded memory and block the event loop for other connections. Holo enforces these as fixed defaults in 0.4.0 and does not expose them as configuration.
- `queue:listen` forwards `SIGINT` and `SIGTERM` to its worker, waits for the worker to close before a restart or exit, and stops with the error when the worker reports a process error while it is being stopped instead of starting a replacement. Laravel's `queue:listen` forwards no signals and respawns its worker after every exit regardless of exit code. Node does not kill a child process when its parent exits, so an unforwarded signal leaves a worker running with nothing supervising it, and a replacement started after a process error may run beside a worker that never closed; both would let two workers process the same queue.
- Login attempts use Laravel's 200 ms timebox, which returns early only after the credentials check passes, so a failed attempt takes the same minimum time whether or not the account exists. Reset-link requests use the same minimum on every path, including a successful send, and never return early, because a found account's mail send would otherwise make its response slower than an unknown account's padded one. Laravel's login timebox can return early on success because a valid login already proves the password; a reset request on the found path has no equivalent proof, so the reset timebox is a hardening departure.
- `timeoutMs` and `AbortSignal` never interrupt a commit or rollback, including a savepoint's release or rollback. Laravel has neither option, and Node can time out a commit that the database still completes; the caller would then be told the transaction rolled back while its data is saved. Only starting a transaction and individual queries can be bounded.
- After a failed COMMIT, Holo issues a ROLLBACK on the connection and ignores that rollback's error, where Laravel only decrements its transaction level. SQLite can leave a transaction open after a failed commit, and the next transaction on that connection would fail to start. The commit error is still the one reported, and `afterRollback` callbacks do not run, because the commit's outcome is unknown.
- Savepoints on one transaction run one at a time, and a transaction call made from inside a savepoint's async work nests under that savepoint. Laravel gets this from its single thread, where nested calls run in order. Node runs concurrent async work on one connection, so Holo queues sibling savepoints and finds the active transaction through the async call chain. A call from an unrelated async chain waits for the running savepoint instead of attaching to it, and a call from inside a savepoint never waits on the savepoint that is waiting for it. Async work that resumes after its savepoint has finished joins the nearest open transaction, and a call on a connection whose transaction has finished throws, so no callback is registered on a closed savepoint. A savepoint's `afterRollback` callbacks run inside the transaction that contains it, because that transaction is still open and a call from the callback must not wait on the savepoint that is waiting for it. Transaction lifecycle logger hooks run before their savepoint or transaction takes its queue or scheduler gate, so they may run database work. Query logger hooks run outside the scheduler slot. `onQueryStart` runs before its query queues for a slot, and `onQueryError` runs after the slot is released, so a hook may run database work on the same connection. Queries issued from inside a query hook do not run the query hooks, so a hook cannot re-enter itself through a saturated connection. A hook inside a transaction or savepoint that waits on work needing that transaction's connection gate, such as a query that a single-connection pool can run only after the transaction ends, still deadlocks, because the gate waits for the hook. Removing that wait means not awaiting hooks inside a gate, which changes how a hook error reaches the query, and it is left for a later ticket.
- `attempts` retries a transaction only after the driver reports a concurrency error by code: SQLSTATE `40001` and `40P01`, MySQL `ER_LOCK_DEADLOCK` and `ER_LOCK_WAIT_TIMEOUT`, and SQLite `SQLITE_BUSY` and `SQLITE_LOCKED`. Laravel matches the message text, which changes with the server's language and version, so Holo matches the stable codes that the drivers expose.
- `whereColumn()` accepts only the comparison operators `=`, `!=`, `>`, `>=`, `<`, `<=`, and `like`, and other operators throw `SecurityError`. Laravel accepts every operator in its list, including bitwise and regular-expression operators, but Holo writes the operator into the SQL text instead of binding it, so an unchecked operator would be SQL injection. The allowlist matches the join operators.
- PostgreSQL `date` and `timestamp` values are read and written in `app.timezone` (default `UTC`), not the Node process's time zone. A `date` reads as a `Date` at midnight in that zone, a `timestamp` is its wall-clock time in that zone, and a `Date` query value is sent with its offset. Laravel formats dates in `app.timezone`. Laravel returns dates as strings, and Holo types a `date()` column as `Date`, so the zone that turns a day into an instant has to be fixed by the framework rather than by the process. On a day the zone skipped entirely, there is no local midnight, so a `date` resolves to the next day, as Laravel's Carbon does, and a load-then-save stores that day. This is a documented limit (#199), and `APP_TIMEZONE=UTC` avoids it.
- MySQL `date`, `datetime`, and `timestamp` values are read and written in `app.timezone` too. Laravel's MySQL session zone is its configured `timezone` (`+00:00` by default), and Laravel formats dates in `app.timezone` in PHP. Holo departs by setting every pool connection's session time zone to `app.timezone`, because a `DATETIME` is a wall-clock time and a `TIMESTAMP` is an instant, and both are right only when the session zone is the application zone. Named zones need MySQL's time zone tables, and without them queries fail rather than store shifted `TIMESTAMP` values. In the repeated hour when clocks fall back, MySQL shows two instants with the same wall-clock text, so a `TIMESTAMP` stored at the later instant reads back an hour early and saving it back stores the earlier instant. That is a limit of the wall-clock session. Injected `client` and `pool` objects keep their own settings, because converting their dates without their session zone would make values shift; When an app opts out of driver date conversion with `dateStrings` or `typeCast: false`, the stored strings are returned as they are; they are already in `app.timezone`, so the opt-out keeps values app-local rather than bypassing the zone. This is a Node-safety departure.
- Eager loads split their key lists into chunks of at most 256 keys, and each chunk runs its own query, where Laravel's `whereIn` sends every key in one query. Node's drivers bind each key as a parameter and reject a statement past their bind limit (PostgreSQL 65,535; SQLite 999 before 3.32 and 32,766 after), so a list of thousands of parent keys would fail where Laravel succeeds. Chunks are padded by repeating their last key up to the next power of two, so every query uses one of nine IN-list sizes. MySQL caches prepared statements per connection (256 by default) and keeps one entry per statement text, so unpadded chunks of every size would churn that cache. A constraint with `limit()` or `offset()` isn't chunked: its pagination applies to the whole eager query, as in Laravel, so that relation runs as one query, and a very large parent set is bound in one IN list. Results match Laravel; a constraint callback runs once per chunk, and for one-of-many relations twice per chunk (once for the grouped lookup, once for the outer query). Lazy loads (`load()`) take the same chunked path as eager loads, so the boundary between them does not change results or query shape.
- Schema referential actions (`onDelete()` and `onUpdate()`) accept only `cascade`, `restrict`, `set null`, and `no action`, and other values throw `SchemaError`, because the action is written into the DDL text. The four accepted actions are the ones Laravel's blueprint methods document.
- A failed login for a missing account runs the configured password verifier against one dummy digest, made once per configured hasher and cached, so it costs what a failed login for an existing account costs. Laravel relies on its Timebox alone, which equalizes timing only while verification finishes inside the floor; a high-cost hasher would otherwise reveal which accounts exist. The floor stays at 200 ms.
- Remote media downloads refuse URLs and resolved addresses that point at local or private networks, including IPv6 addresses that carry a local or private IPv4 address, and refuse the whole block reserved for local use, because its IPv4 position depends on the deployment's configuration. Holo fetches user-supplied URLs from the server, where they could reach internal services. Laravel core has no remote-media fetch, so there is no Laravel behavior to match; this guard is a hardening departure.
- Password digests use scrypt with N = 2^15, r = 8, p = 3 and a 64 MiB memory limit, and a process runs at most four scrypt operations at once, queueing the rest. Laravel's bcrypt default of 12 rounds is not an equivalent memory-hard setting. The cost follows the OWASP Password Storage Cheat Sheet's scrypt table, which lists N = 2^15, r = 8, p = 3 (32 MiB) as equivalent to N = 2^17, r = 8, p = 1 (128 MiB) (<https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html>). The concurrency bound keeps peak scrypt memory near 128 MiB whatever `UV_THREADPOOL_SIZE` is. Digests made at older settings are replaced on login by the built-in database providers, through one conditional write that applies only if the stored digest still matches the verified one, so a password reset landing between verification and the write is never overwritten. Custom providers keep their digest until the password changes, because a custom adapter has no compare-and-set capability and a plain save could overwrite a concurrent reset. Laravel's `rehashPasswordIfRequired` is also a plain save, so the conditional write is stricter than parity, and the atomic write is the hardening departure. This is a hardening departure.
- A scheduled `call()` without a `name()` can use `withoutOverlapping()` and `onOneServer()`, where Laravel throws until the closure is named. Holo names an unnamed function by its source text and cron expression, so every server running the same `server/schedule.ts` derives the same lock key. Holo's commands and jobs take generated names when none is given, and the scheduler follows that convention. Two unnamed functions with identical code and frequency share a lock.
- `schedule.job()` takes a job definition and its payload, `schedule.job(SendDigest, { userId: 1 })`, where Laravel takes a job instance, because a Holo job is a definition plus a JSON payload rather than a class instance.
- `schedule:work` forwards `SIGINT` and `SIGTERM` to the `schedule:run` processes it started, and `schedule:run` forwards them to the command it is running and starts no further tasks; each waits for its children to exit before it exits. Laravel's `schedule:work` and `schedule:run` forward no signals. Node does not end a child process when its parent exits, so an unforwarded signal would leave a `schedule:run` or its scheduled command running unsupervised, as with `queue:listen`.
- `schedule:run` decides which tasks are due from the time the command started, where Laravel reads the clock after the application boots. Holo bundles the app's schedule and definitions before it can evaluate them, and a boot that crosses a minute boundary would otherwise skip the tasks due in the minute cron started it for.
