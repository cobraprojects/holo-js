# The Database schema is the only schema source

Holo keeps no record of an application's tables besides the database itself, as Laravel does. Migrations change the Database schema and record only that they ran, in the single `_holo_migrations` table. Nothing else describes the schema: there is no in-memory schema registry, no metadata kept beside DDL, and no replay of migrations to reconstruct one. This supersedes [0003](0003-schema-mutation-metadata-ownership.md). The implementation is tracked in #470; until it lands, the registry and replay described below are still in place.

We chose this because every earlier attempt to keep a second description of the schema drifted from the database. The description lived in process memory and in a gitignored artifact. To rebuild it, Holo replayed migration history, and no rule for reads during replay made that correct: forwarding reads to the live database crashed when a later migration had dropped a table an earlier one read, while answering them with empty rows silently lost tables a migration created only when a query returned rows. Persisting the description in the database would remove the replay, but it still duplicates what the database already holds and needs a one-time conversion for every existing database. Laravel needs neither.

Consequences:

- The schema builder is stateless. `change()` replaces the column definition with exactly the modifiers given, as Laravel's does, and operations that need the current table read it from the Database schema. SQLite table rebuilds take their columns, indexes, and foreign keys from the database, so columns the migration did not declare are preserved.
- The Generated schema is produced from the Database schema after `holo migrate`, `holo migrate:rollback`, `holo migrate:fresh`, and `holo build`. A model's attribute types take each column's type from it, overridden by the model's `casts` where the database cannot state a value's type. This is Holo's departure from Laravel, which generates no types. Holo depends on typed models, so it derives them from the same sources Laravel uses at runtime: the database and the model's casts.
- On SQLite, columns are created with Laravel's type names (`tinyint(1)` for booleans, `datetime`, `date`, `varchar`) so the database can state them. JSON columns are `text`, as in Laravel, and are typed as JSON only through a `json` cast. Tables created before this decision keep their stored types.
- `holo migrate --isolated` takes an atomic lock from the application's cache store, as Laravel's does, so it requires a lock-capable store shared by every server. The `_holo_migration_locks` table is no longer created.
- Schema operations and markers that exist only to maintain a second description are removed: registry-driven `sync()` and `previewSync()`, metadata-only `generated()`, and the unused migration planning surface.
- Verification runs real SQLite, PostgreSQL, and MySQL databases through the CLI and the schema builder, and asserts on generated types and on the Database schema.
